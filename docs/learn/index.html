How to use this

Each stage opens with one prerequisite sentence — a concept you must already hold or the code reads as syntax. It closes with self-check questions. Answer them out loud before moving on. If you cannot, re-read the stage; that is the whole method.

Stops marked optional are depth. Skip every one and you can still explain the system end to end — you will just have less to say about the corners.

Two honest caveats, before you invest the time

The harness is built and test-verified. The campaign has not run. No number in this project has yet come from real hardware. You are learning an instrument that has been proven against itself and against Docker, and is waiting on its first billed deployment.

The external links were correct as of mid-2026 and may have moved. Where a resource has a stable identifier (an arXiv number, a DOI, a project's own domain) I give it. Where I only have a title, search that title.

What this project is, in one paragraph

Seven systems that solve the same problem — consensus, getting several machines to agree on the same ordered sequence of values while some of them fail — are benchmarked under one identical load model, and the result is a master's thesis. The systems are etcd (Raft), Kafka KRaft (Raft), Kafka + ZooKeeper (ZAB), CometBFT (Tendermint BFT), Paxos and EPaxos (both via the Paxi research framework), and HotStuff (BFT).

The one sentence that explains every design decision

A previous version of this project measured each system with a different client stack, and shipped a deployment layer that had never once been executed. Both failed. Every structure you are about to read is a countermeasure to one of those two failures: one load model for all seven systems, and every remote command reviewable by a human before a euro is spent. The javadoc blocks name the specific bug they prevent, with a finding ID — F13, F50, F70. Read them. They are the curriculum this repo already wrote for itself.

Self-check — Stage A
Why do CometBFT and HotStuff default to 4 nodes when the others default to 3?

They are Byzantine-fault-tolerant. Crash tolerance needs 2f+1 nodes to survive f failures, so 3 tolerates 1. Byzantine tolerance — surviving nodes that lie rather than merely stop — needs 3f+1, so tolerating 1 requires 4. The enum encodes each protocol family's minimum honest shape.

If only the post-warmup histogram produces thesis numbers, what is the other one for?

Debugging the warmup itself — "was the system still ramping?" is a question you cannot ask once you have thrown the warmup samples away. It is diagnostic and is never reported.

B

The measurement engine — the heart

Before you startYou must hold the difference between an operation being sent and an operation being committed. And you must accept that the rate at which you offer work and the rate at which a system completes it are different things — a client that waits for a reply before sending again has silently made its own load depend on the system's speed.

5
core/WorkloadEngine.java293 lines · the single most important file

Open-loop load generation with a bounded in-flight window, and correction for coordinated omission.

Read first — run(), lines 102–188. Everything else supports it. Go slowly over lines 122–163: the fixed departure schedule, the semaphore window, and the callback that charges latency against the intended time.

Coordinated omission — the idea the whole thesis rests on

A system freezes for one second. Your client is blocked waiting for a reply, so it sends nothing during the freeze and records one slow request. But at 100 ops/s, a hundred requests should have departed in that second, and every one would have queued. Your histogram omits them — because the stall coordinated with your sending. That is coordinated omission, and it makes a stalling system look fast.

The fix is three lines. Capture the scheduled departure time, and charge latency from that:

// WorkloadEngine.java:135
final long intended = openLoop ? nextIntendedNanos : System.nanoTime();

// WorkloadEngine.java:147-149
// Coordinated-omission-corrected latency: completion minus
// INTENDED start, not minus actual send.
final long latencyMicros = (completed - intended) / 1_000L;

It is proven, not asserted, by WorkloadEngineTest.stallLatencyIsChargedAgainstIntendedTime (line 98): a 1 s stall in a 3 s run must push p90 above 300 ms.

src/test/…/core/FakeDriver.java optional104 lines, test scope

Read first — stalling(long, long, long) at line 42.

Self-check — Stage B
A system freezes for one second during a run at 100 ops/s. How many slow samples appear under (a) naive send-time measurement and (b) this engine?

(a) About one. The client was blocked waiting, never sent the other ~99, and unsent operations produce no samples. (b) About a hundred. The schedule fixed all 100 intended departure times before the run; each is charged completed − intended, so each carries its own queueing delay.

The engine drains by acquiring every in-flight permit, then immediately releases them. Why not just hold them?

Occupancy is computed as maxInFlight − availablePermits(). Holding them would leave availability at zero, so a metrics scrape landing during the drain would read a full window when nothing is in flight — recording a spurious peak that fails the window_headroom validity gate on a perfectly clean run. The instrument must not create the artifact its own gate detects.

A fault run's event buffer fills before the fault is even injected. What does failoverMillis() return, and why is that dangerous?

Empty — no qualifying commit was recorded after the mark. It is dangerous because "the fault fired and nothing ever recovered" looks identical, and that is a real, preregistered result for Paxi. Two opposite readings, the same numbers. The countermeasure is events_dropped in the manifest plus a narrow rule: only "fault fired and evidence dropped and no failover resolved" voids the run, so a late overflow does not discard a recovery already recorded.

C

Drivers — one transport per system

Before you startYou must know that "committed" means something different in each protocol — a Raft majority acknowledgement, a Kafka acks=all in-sync-replica acknowledgement, inclusion in a CometBFT block with more than two-thirds precommits, a Paxi HTTP 200 meaning committed-and-executed. A driver's only job is to translate one abstract write into whichever of those its system offers.

Self-check — Stage C
EtcdHttpDriver.currentLeaderIndex() returns empty. Why would returning 0 be dangerous rather than a harmless placeholder?

It is constructed with a single endpoint and structurally cannot know which member leads. A confident 0 would be consumed by the fault targeting logic and used to pick a node to kill — and etcd's leader is whichever member won the first election, so roughly two-thirds of leader_kill cells would silently have measured follower loss instead. The results would look perfectly clean and answer the wrong question.

Why does Paxos pin every write to one endpoint while EPaxos round-robins?

They test different things. Paxos has a leader; a non-leader entry point just forwards internally, so pinning is honest. EPaxos is leaderless — its whole claim is that any replica can commit non-conflicting commands on a fast path — and sending all traffic to one endpoint could never exercise that.

D

Topology and faults — where a mistake costs money

Before you startYou must know quorum well enough to predict a kill: on 3 nodes, killing one leaves 2 — a majority, the cluster survives. Killing two leaves 1 — no majority, the cluster stops committing, and that stop is the intended observation. You must also know that a network partition is not a crash: a partitioned leader is still running and still believes it leads.

What a "golden file" is, and why this project lives on them

A golden file is a checked-in, human-reviewed transcript of exactly what a program will do, which a test then compares against byte for byte. Three pieces: SshExecutor (the seam), RecordingSshExecutor (a test implementation whose whole trick is one line — commands.add(host + ":" + port + "$ " + command)), and seven transcripts in src/test/resources/goldens/, 681 lines total.

Why here specifically: these commands run on billed machines, and Java's type system cannot tell you that eth0 is the wrong network interface on a Hetzner box, or that a subnet-wide firewall rule would sever the very path you are measuring. A person reading the golden's header can. Each golden opens with a paragraph listing the invariants a reviewer must confirm — the file is a review document that happens to also be an assertion.

Self-check — Stage D
partition installs pairwise DROP rules per peer IP, never one rule against the whole subnet. What breaks if you "simplify" it?

The load generator lives on the same private subnet. A subnet block would cut the client→leader path too, so the client would just see timeouts from an unreachable machine. But observing the isolated leader — still running, still believing it leads, no longer able to reach a quorum — is the measurement. A test asserts that neither the subnet nor the loadgen's IP appears anywhere in the emitted commands.

Every mutating method on SshFaultInjector is synchronized. What concrete bug does that prevent, and why would nothing downstream catch it?

Injection runs on the fault thread while heal() runs on the main thread after a join that can time out. Interleaved, heal deletes the traffic-shaping rule before it has been added; the delete fails as "nothing to undo" — a warning, by design — and the rule then survives on the node, silently shaping every later run there. Nothing catches it afterwards: the pre-clean sweep removes stray containers, not host network state.

On a healthy node the pre-clean commands are all expected to FAIL, and exit code 0 is treated as an alarm. Explain.

With nothing to undo, the undo commands exit non-zero — that is the normal case. A zero exit proves fault state really did survive a crashed earlier run, which also puts that run's data in question. So zero is warned about, with the node and the command named. This deliberately inverts heal()'s convention, where the fault is known to have been applied and non-zero is the surprise. Neither path uses || true, because that would discard the one bit that distinguishes them.

Results and judgement — what makes it a thesis

Before you startYou must accept that a measurement is only evidence if its preconditions held — and that those preconditions are themselves measurable facts about the run: the client was not saturated, the clocks agreed, nothing restarted unexpectedly, the fault demonstrably landed. Without that framing the next file looks like defensive programming. With it, it is the experimental protocol.

validity/ValidityChecker.java784 lines · the file that makes the thesis defensible

Read first — check(Path runDir), lines 189–218: twenty lines naming all eleven gates in order. Read that, then the class javadoc at 17–52, then individual gates on demand.

The rule that carries the most weight: empty ≠ absent

If metrics/ exists but a series a gate needs is empty, that gate FAILS. Only the whole-feature-absent case is SKIP.

An empty series means somebody tried to retrieve the metric and got nothing: a wrong label, a dead scrape target, a broken query — a malfunction. A malfunction in the observation apparatus is precisely when a gate must not wave a run through, because you no longer know what you measured. If empty meant "nothing bad found", broken monitoring would manufacture clean runs, and the more broken it got, the cleaner the data would look.

A missing directory is different: the export never ran, no capability malfunctioned. Failing there would invalidate runs for lacking infrastructure they were never given. Two consequences worth noticing: the exporter writes the file even when the query returns nothing, so a header-only CSV proves the query ran; and a missing error_rate in a manifest FAILs rather than passes, because an unmeasured error rate is not a zero one.

validity/ConfidenceGrade.java120 lines

How far a cell — one configuration measured five times — can be trusted, as an ordinal grade with named reasons. Adapted from GRADE, the medical evidence-rating framework, whose vocabulary the thesis then borrows rather than inventing its own.

Read first — of(...), lines 72–119. VOID / C / B / A. VOID is this project's addition to GRADE: a level for "this evidence cannot evidence its own claim", a failure mode that does not arise in a literature review but arises here twice.

Self-check — Stage E
metrics/ exists and contains loadgen_cpu.csv, but the file has only a header row. PASS, FAIL or SKIP?

FAIL. The directory's existence proves the export ran, so an empty series means the retrieval path is broken, not that nothing was collected. Contrast: no metrics/ directory at all ⇒ SKIP, because a capability was simply absent — the two-VM canary shape has no observability machine, and failing there would invalidate runs for lacking infrastructure they never had.

Five runs, all valid, every evaluated gate passed — but three gates SKIPped for want of an observability VM. What grade?

B, with the reason "indirectness: gate(s) not evaluated" — and the grade must name which gates, since "B" alone tells a reader nothing about what to be careful of. Not A, because the claim rests on fewer checks than the methodology specifies; not C, because nothing that ran failed.

A leader_kill run finishes with 89,400 commits, a 0.23 % error rate and beautiful percentiles — but the manifest's fault timestamp is null. What happens, and why is this the most important case in the layer?

Two things fire: the writer forces "status": "failed", and the fault-ground-truth gate fails the run rather than reporting "baseline — not applicable". It matters most because the mark is stamped only after the injection returns, so its absence means the injection threw or stalled — and what was actually measured is an undisturbed cluster wearing a leader_kill label. Every number is real; the experiment is not. Judging by the mark alone previously reported this as a baseline and waved it through. It is the origin of the VOID grade.

Self-check — Stage F
MatrixRunner shuffles a block's cells with a seeded Random. Why shuffle, and why seed?

Shuffle, because running all baselines then all faults would confound the comparison with time-of-day effects on shared cloud infrastructure. Seed, because the order itself must be reproducible — the seed is logged and written into the simulation spec, so anyone can reconstruct which cell ran when.

Main.parse accepts any --key value pair, yet --ratee 300 is rejected. Where, and why does it matter?

In requireKnownKeys, against an explicit allow-list. Because --ratee 300 parsing fine and the run proceeding at the default rate is a fail-open in an otherwise fail-closed tool. The manifest would faithfully record the truth — but only after a wasted, or worse a trusted, run.

The tests — and how to run just one

248 tests in 37 classes. They are not one thing; they buy five different kinds of confidence, and knowing which is which is most of what a reviewer wants from you.

KindWhat it proves
UnitThe arithmetic and the branching are right. Given X, the code decides Y. Proves nothing about the world.
Golden-fileA human reviewed exactly what a billed VM will run. No SSH, no Docker, no euro.
ContractTwo files that must agree cannot drift apart silently. Unusual, and worth pointing out — it tests the seams between artifacts, not behaviour.
IntegrationThe world behaves as the code assumes. Unit and golden can both be green while reality is broken — this project has a documented instance of exactly that.
RegressionThe specific catastrophe that killed the previous attempt has not come back.

The signature move: eight tests deliberately damage something to prove a check can fail. A manifest is written as literal {not json; a metrics file is written with only a header; two of three real etcd containers are killed and the write must fail rather than fabricate a commit. As this repo puts it — a check that cannot fail is worse than no check, because it produces confidence instead of information.

Read these six, in this order

  • core/WorkloadEngineTest.java — 19 tests. Start here. The production code asserts that latency is charged against intended time; this demonstrates the consequence.
  • topology/RemoteSshProviderTest.java — 21 tests. The only place you can see the whole deploy layer without reading 896 lines.
  • validity/ValidityCheckerTest.java — 38 tests, the largest. The gates' reasoning is in the production javadoc; their boundaries are only visible here.
  • topology/SshFaultInjectorTest.java — makes a concurrency bug deterministic with two latches. A technique worth stealing.
  • topology/HostFaultEffectTest.java — the explicit answer to "the goldens are green, are we done?" Its javadoc says no, and names the bug that proves it.
  • driver/EtcdDriverTest.java — cross-validates leader detection against an independent client stack. Two stacks agreeing is corroboration; one stack agreeing with itself is circular. A research-methods lesson inside a unit test.
